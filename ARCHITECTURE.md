# Architecture

This package supplies concrete syntax trees and ordered highlight captures for CSS and SCSS. It is not a Sass evaluator, CSS validator, editor, or document store. The [consumer contract](README.md#consumer-contract) defines the public behavior; this document describes its implementation boundaries.

## Ownership and dependency direction

```text
grammar.js ── generator ── src/parser.c + schema + runtime headers
src/scanner.c ─────────────┘
                            ├── Node binding ── native acceptance tests
queries/highlights.scm ──────┤
                            └── Rust/native binding ── native acceptance tests

scripts/grammar.js ── CLI / native build
        ↑
scripts/preview.js ── fresh inspect.js process + standard CLI highlighting
        ↓
preview-client.js ── temporary browser draft
```

| Boundary                           | Owns                                                                            | Does not own                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `grammar.js`                       | Syntax structure, fields, precedence, block contexts and external-token order   | Editor completion, semantic evaluation or runtime caches            |
| `src/scanner.c`                    | Lexical context, bounded pairing, dialect identity and CSS lexer adaptation     | Document state, source mutation, history or persisted scanner state |
| Generated `src/` files             | Reproducible projections of the grammar and generator version                   | Independent handwritten decisions                                   |
| `queries/`                         | Portable capture names and their ordered overrides                              | Host colors, fonts or editing commands                              |
| `bindings/node/`, `bindings/rust/` | Native language exports and access to schema/query                              | Build orchestration and preview lifecycle                           |
| `scripts/grammar.js`               | Checkout root, CLI executable/options/cache, generation and native build        | Syntax decisions or preview state                                   |
| `scripts/benchmark.js`             | Sample timing, per-dialect parser/tree lifetime and process resource reporting  | Parser allocation policy, editor latency or document history        |
| `scripts/fuzz.js`                  | Seeded random-edit recording and baseline/candidate comparison                  | Parser policy or acceptance decisions beyond its exit rules         |
| `scripts/preview.js`               | HTTP requests, file watching, build invalidation and published preview revision | Durable documents or browser drafts                                 |
| `scripts/preview-client.js`        | Draft text, one active generation request, focus restoration and update notice  | Parser lifecycle or source-file writes                              |

The Tree-sitter runtime owns trees and incremental reuse. A host edits the old tree before reparsing; undo is another host edit. No parser-local history or second source model exists. Native packages include generated C and headers so installing them does not require the generator. Their file lists are checked rather than inferred from repository layout.

## Invariants

- CSS and SCSS share one generated parsing table, node schema and query. Language selection is immutable per entry; it is never a global dialect switch.
- The scanner serializes zero bytes. Every lookahead context belongs to one call and is discarded on return.
- Whitespace before a colon has one external token shared by declarations and selector combinations. The grammar resolves those readings; the scanner does not repeatedly search for a block after each spaced pseudo. Cross-line recovery retains its existing lookahead window.
- Statements being typed end at a hidden statement break or, for an at-rule header or a line of leading punctuation, at a token no state accepts. Every site that emits one is listed in [Statement breaks](#statement-breaks).
- Each statement-break lookahead helper spends at most 1,024 steps, whitespace, comments and interpolation included. Interpolation pairing spends its caller's budget and charges each nested opener 64 more steps until it closes; deciding whether an opener in a comment or string is literal starts with the whole budget. Local frame capacity is derived from that bound, including the final opener that exhausts it. There is no independent depth policy, recursive scan, heap growth or frame cleanup path.
- The CSS descriptor is published once with acquire/release synchronization. This protects concurrent native callers and must not be replaced with an unsynchronized flag.
- CSS CRLF normalization preserves original positions in the main lexer. Literal keyword matching shares the generated keyword lexer directly; it has no identifier escapes to normalize. External scans retain their own dialect-aware escape routine.
- `pnpm generate` removes Tree-sitter's optimize-off pragma from `src/parser.c`, and `--check` applies the same step before comparing. The generator adds it for any large lexer, assuming lexing is cheap; here the lexer is about a quarter of parse time, and keeping it optimized cuts corpus CPU time by about 14% and the parser object by about 19%, for several more seconds of compilation. An unrecognized pragma fails generation instead of silently compiling the lexer unoptimized.
- Grammar external-token order and the scanner enum must agree. Generate and test after changing either side; never hand-edit generated C to change syntax.
- Public nodes, fields, anonymous punctuation, ranges, ERROR/MISSING status and ordered captures are compatibility surfaces. “Both parses succeed” is insufficient equivalence evidence.
- All development CLI invocations go through `runTreeSitter`, using `build/tree-sitter` in the current checkout. A same-named grammar compiled elsewhere cannot supply its library.
- Foreground test/parse/highlight commands inherit the terminal and keep the CLI's running lifetime. Internal generation/preview calls capture output with a 30-second timeout and 16 MiB limit. Both modes share the same executable, checkout and cache policy.
- Build-source edits invalidate the preview binding. A fresh inspector process loads the rebuilt native module; source-only edits and browser drafts do not rebuild it. Drafts never overwrite fixtures.

The interpolation budget bounds temporary storage and nested scanning. It does **not** prove that every scan or complete parse is linear: identifier/trivia scans and statement lookahead have separate costs.

## Statement breaks

A statement being typed ends where the next line begins a declaration. The scanner marks that boundary with a token the current state rejects, so recovery returns to the enclosing statement list: a hidden statement break, which statement lists and raw statement items accept, or, for an at-rule header or a line of leading punctuation, a token no state accepts, so the parser skips that line as one error. Tree-sitter recovers by returning to the first earlier state that accepts the current lookahead, then lexes again from the end of the last node it kept; every site below relies on this.

Most sites use one of two checks. The name-level check, `declaration_name_follows`, wants a name, which may carry the `*` hack or interpolation, then a colon no pseudo-class takes; a selector line needs no more, because a last declaration may omit its `;`. The line-level check adds `declaration_line_rest`: the value ends with `;` on that line, outside any group still open around it, so map entries, arguments and CSS `if()` branches never qualify. Three sites vary them, as the table shows: S4 outside a group skips the group test, S5 continues a partly read name, and S8 reads its payload as the name. An exhausted lookahead budget makes a line no declaration, except in the group test, where it counts as no group.

| Site | Scanner context                                                               | Next line                                                                                     | Token                                                                                            |
| ---- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| S1   | Whitespace in a selector state crosses a line                                 | Name-level                                                                                    | Statement break, or the `*` hack's line token after `*`; zero width at the end of the line above |
| S2   | Punctuation that cannot complete a selector ends its line                     | Name-level, after any comments                                                                | Statement break including the punctuation                                                        |
| S3   | A statement list lexes that punctuation again after recovery                  | Name-level, after any comments                                                                | Statement break including the punctuation                                                        |
| S4   | `@` at a statement start, or `@else` where an `@if` block may end             | Name-level and a `;` on that line, line-level inside a group, before the header's block opens | The never-valid header token, covering the header; for `@else`, also the trivia before it        |
| S5   | A name on a later line of a declaration value                                 | Line-level, with the name partly read                                                         | Statement break, zero width at the end of the line above                                         |
| S6   | A line-leading `*` in a declaration value                                     | Line-level                                                                                    | Statement break, zero width at the end of the line above                                         |
| S7   | A later line inside an unclosed Sass `url(`                                   | Line-level                                                                                    | Statement break, zero width at the end of the line above                                         |
| S8   | A later-line CSS `url(` payload that is exactly `name:` before whitespace     | Line-level after that colon                                                                   | Statement break including the payload                                                            |
| S9   | A line-leading `>`, `+`, `~` or `#` at a statement start, or `#` after spaces | Name-level, after any comments                                                                | The never-valid header token, covering the punctuation                                           |

- **Selectors (S1–S3).** Only a declaration on the next line ends a selector line at whitespace; anything else continues the statement as a descendant, because a break before `}`, the end of input or another selector line leaves two adjacent errors that recovery can merge with the rest of the file. A spaced colon on its own line continues the selector when lookahead reaches its block or the close of a group around it before a `}` or `;`, or runs out of budget. The `*` hack has its own line token, so a separator after `*` still ends its line. Never emit the break at a compound start, where identifier recovery commonly lands.
- **Punctuation (S2, S3).** A break at trailing punctuation must include it, because the runtime ignores an empty external token until parsing has advanced past an earlier error, and reusing a recovered subtree changes when that happens, so an incremental parse would differ from a fresh one. The recovered list lexes that punctuation again, so it claims the punctuation as a break when no line break comes before it; otherwise the second error merges with the rest of the file, as it did for selectors of several compounds. That also hides the same punctuation after another statement on its line. A token no state accepts there would be reported, but recovery then merges it with the rest of the file. A stray separator at the start of its own line remains an error.
- **Headers (S4).** The claimed at-rules are the Sass directives `@if`, `@each`, `@for`, `@while` and `@at-root` as spelled, and `@media`, `@supports`, `@container`, `@layer`, `@scope` and `@starting-style` in any case. The scanner cannot tell the top-level statement list from a block's, and no declaration may follow a header at the top level, so claiming the header of an at-rule usually written there, such as `@mixin` or `@font-face`, would strand its body before the next rule. Inside a group only the header's first line break counts, and only when the group never closes, so a header runs the declaration checks at most twice. A comment after the header stays outside the error, but an `@else` token starts where the `@if` block may end, so it also covers the whitespace and comments before `@else`. Other spellings, other at-rules and an `@else` with no `@if` keep their own recovery.
- **Values (S5, S6).** A declaration value is a state where `!important` and a keyword token are valid; maps, arguments and raw custom-property values are not. Sass reads a line-leading `*` as multiplication, but a `*` hack declaration still ends the value. Expression positions in general never emit the break: they are also the states inside maps and arguments, where a break damaged recovery far from the edit.
- **URLs (S7, S8).** A Sass payload never holds a declaration. The CSS break includes the `name:` payload rather than ending at the line above, because the payload end is marked before the declaration lookahead so that a payload starting no declaration keeps its own end.
- **Leading punctuation (S9).** A statement list shifts a line-leading combinator, or the `#` of an interpolation, as the start of a selector, and no other site reaches that line: the states after a combinator accept no descendant, S3 skips only spaces and tabs, so it never reaches punctuation after a line break, and an empty interpolation's `}` can close the enclosing block. When the line holds only the punctuation S2 accepts, empty interpolation included, and a declaration follows, the scanner claims it with the never-valid header token rather than a break, so the stray line stays a reported error. S3 claims a `#` only where it touches the token before it, so a `#` after spaces on its line, even after another statement, reaches this site too and is reported, as a spaced `.` or `:` there is. After an earlier error on the statement, such as a stray `,`, recovery returns to the same statement list, so the token becomes a second adjacent error and merges with the rest of the file, as the punctuation rule warns. `UNFINISHED_HEADER` therefore names any token no state accepts at a statement start, not only a cut-off at-rule header. The characters stay explicit rather than `selector_separator`, which adds `,` and `(`: those already stay local errors at the start of a line, and claiming them would only change their trees.
- **Width.** A break decided across a line at S1 or S5–S7 ends at the end of the line above and leaves the whitespace to the next token. An error that then reaches into the next line pays for the line break, so recovery reports the unfinished line rather than the start of the declaration below it, and a value that ends with a dotted name, which takes no missing `;`, becomes one error. A value that ends with interpolation instead lets the next declaration's name join the error; over typed values and random edits the placement still recovers more declarations than a break at the start of the next line. These breaks are empty in the runtime's sense, which the punctuation rule warns about. They stay consistent because the token before each one, a selector, a value or a header, has width, so parsing has advanced past any earlier error; a break right after a missing token or at an earlier error could be dropped in one parse and kept in the other.
- **Adding a site.** Start from this table: name the context signal the scanner reads, choose the name-level or line-level check, and state the token's width; then require zero remote capture loss in a [random-edit comparison](#independent-validation) over long stylesheets recorded with `--corpus`. One shared break for every expression position was measured and rejected, and so was one grammar rule for every group's content, which removes the context signals these sites read.

## Independent validation

After `pnpm build`, `pnpm test:node` runs native parser/schema/highlight/editing tests without starting the preview server. `pnpm test:development` tests generation, real CLI isolation, HTML generation, browser request state and the HTTP watcher lifecycle. `pnpm test:parser` checks corpus trees and CLI highlighting; `pnpm test:rust` checks the other runtime/binding boundary.

`pnpm test` retains parser, Node and development coverage. `pnpm check` additionally requires lint, formatting, generated-file equality, Rust tests/formatting, package contents and preview export. The generated parser has a 525-large-state budget; it is not a performance score or permission to weaken behavior.

Two-copy CLI tests intentionally compile distinct root-node names under the same grammar name, switch back to the first copy, and check diagnostics for malformed input. Pairing tests characterize the visible threshold and exercise 100,000 nested openers. Runtime tests compare incremental/repair trees and captures rather than relying only on `hasError`.

`pnpm test:fuzz` replays 5,000 seeded single edits per entry over the highlight fixtures, examples and corpus inputs. Each case parses the edited text fresh and from the edited original tree, then reverts the edit incrementally; the trees must agree on every node's type, field, range and MISSING status. A mismatch fails the run only when the fresh tree it should equal is error-free; other mismatches are reported as runtime and recovery debt. `pnpm test:development` includes a short run.

A grammar or scanner change is judged against its baseline. Rebuild a comparison checkout, then record it and the working tree with the same `--seed`, `--cases` and `--corpus` (a file list as for the [benchmark](#performance-measurements)); inputs always come from the invoking checkout. The list must name long real stylesheets: the remote-loss rule below needs captures more than 300 characters from an edit, and 44 of the 49 repository inputs are corpus snippets under 160 characters.

```sh
node scripts/fuzz.js record --repo /path/to/comparison --corpus /path/to/file-list.txt --out base.jsonl
node scripts/fuzz.js record --corpus /path/to/file-list.txt --out candidate.jsonl
node scripts/fuzz.js compare base.jsonl candidate.jsonl
```

The comparison refuses recordings in another format or of different cases. It fails when an error-free tree changes, or when an error tree changes and loses a remote highlight capture, one more than 300 characters from the edit. It also reports the error-tree differences with their capture losses and gains, split into remote and local, and the incremental and revert mismatches of both recordings. Captures are compared only where trees differ, so a capture-only difference means the queries differ, and a query change also enters the loss counts. A remote loss can also be a relabel: where the baseline's error absorbs the rest of the file, its captures there differ from the unedited input's, so a candidate that restores those captures reports the baseline's as lost. Collapse-prone edits are sparse, so record several seeds and check each remote loss against the unedited input's captures.

## Performance measurements

Run `pnpm benchmark` to rebuild and measure the local native binding. For an already built comparison checkout, use:

```sh
node --expose-gc scripts/benchmark.js --repo /path/to/comparison
node --expose-gc scripts/benchmark.js --corpus /path/to/file-list.txt
```

The optional corpus is a newline-separated list of file paths, resolved from the invoking directory; every file is parsed through both language entries. Output records runtime/platform, source and workload hashes, native/parser size, state counts, module load time, process peak RSS, parse/edit latency and typing counters. Rebuild each comparison checkout first. Source hashes identify inputs; they do not certify a stale native binary.

Full-parse samples have two warmups and nine measured rounds. Before every full-parse round and incremental sample, the runner requests GC when available and yields one event-loop turn so queued native finalizers can run; both steps are outside the timed region. Small/nested samples are batches of 1,000 parses. Incremental samples change one numeric value in a 1,000-rule file and include 20 warmups followed by 200 measured edits. Typing samples type 25 statements key by key into a fresh parse of another 1,000-rule file, inserting a closer with each opener as editors do: `typing-blank` types on a blank line above `width: 1px;`, and `typing-same-line` types before that declaration on its own line. Every key is measured. Each dialect owns its parser and last incremental tree in one async scope, followed by the same cleanup before the next dialect and final resource report. These measure parser work, not GUI latency. `maxRssKiB` is the process peak, while `processRssAfterCleanupBytes` is process RSS after the final cleanup; both include the runtime and benchmark, not just parser storage. `gcBetweenParseSamples` records whether GC was exposed; without it, collection remains automatic.

Without the event-loop yield, native finalizers stay queued even after `gc()`, and discarded trees inflate peak RSS by more than an order of magnitude (about 1.5 GB against 86 MB on Node 24.21.0 / Tree-sitter 0.25.1). The cleanup corrects measurement-induced retention; it does not reduce a live tree's allocation. Because GC and yielding also change heap and cache conditions, compare revisions only with this runner, never against results from a runner without the cleanup.

The spaced-pseudo and multiline-pseudo workloads each contain 20,000 pseudos. They protect the distinction between local token recognition and repeated scanning of the remaining selector. The long-comment-lines workload ends 128 selector lines with a 1 MB comment, which cross-line lookahead must not read in full from every line; comments spend the same step budget as other characters. The interpolated-values workload alternates 500 declarations missing their semicolon with 900-character interpolations; it stays near ordinary parse speed only while every lookahead helper charges interpolation to its own budget instead of skipping it for free. Native acceptance tests also check the complete selector and following rule, without a machine-dependent timing assertion.

Typing timing is noisy, but its counters are deterministic and compare exactly between revisions: `changedKB` sums the changed ranges of every key, `keysChangingQuarterFile` counts keys whose changed ranges exceed a quarter of the file, and `errorKeys` counts keys that leave an error in the tree. A recovery change that lets a typed statement absorb the rest of the file raises the first two. On runtime 0.25.1 both dialects give 53 KB and 2 quarter-file keys over 543 keys on the blank line; those two keys open and close a comment, which legitimately changes the rest of the file. The same-line workload gives 2,005 KB and 40 keys, which is known recovery debt: apart from the comment, each of those keys is half of a pair in which a head that runs into the existing name, as in `.width`, `&width`, `@if width` or `color:width: 1px;`, absorbs the following rules, and a later key, such as the space after the colon or a typed `{`, restores them.

Alternate baseline/candidate order on the same machine with identical hashes. Investigate a repeatable regression in a representative workload before accepting a change. Do not turn one noisy wall-clock result into a CI threshold or claim a speedup from generated size alone.

The 2026-09-30 bounded-storage refactor kept 1,987 states, 478 large states and the 3,961,896-byte parser unchanged. On an Apple M1 Pro, Node 24.21.0 and runtime 0.25.1, same-process alternating measurements gave:

| Workload, median ms                     | SCSS before | SCSS after | CSS before | CSS after |
| --------------------------------------- | ----------: | ---------: | ---------: | --------: |
| 72,918-byte stress fixture              |       4.769 |      4.748 |      5.267 |     5.261 |
| 100 rules                               |       1.098 |      1.096 |      1.126 |     1.124 |
| 1,000 rules                             |      11.058 |     11.076 |     11.121 |    11.171 |
| Numeric edit in 1,000 rules             |       0.239 |      0.240 |      0.240 |     0.240 |
| 10,000 unfinished interpolation openers |      17.547 |     16.672 |      9.062 |     9.079 |

Independent native C measurements over 338 local files / 945,278 bytes were SCSS 76.87 → 76.98 ms and CSS 32.51 → 32.57 ms (seven alternating groups, best of ten within each group, median across groups). Ordinary parsing and editing were effectively unchanged; the measured unfinished-SCSS workload improved about 5%. Initial separate-process Node groups were noisy and are not evidence of a general improvement. The direct resource result is narrower: the scanner no longer references `malloc`, `realloc` or `free`; it uses 16 local frames, 192 bytes on this ABI. No process-wide memory reduction is claimed.

The later Q017 comparison uses clean v0.10.0 as its baseline and identical `-O2` native builds. On the same machine/runtime, seven alternating corpus groups (best of ten within each group, median across groups) and three alternating pseudo-chain samples gave:

| Workload, median ms                         | SCSS before | SCSS after | CSS before | CSS after |
| ------------------------------------------- | ----------: | ---------: | ---------: | --------: |
| 338 local files, selected by file extension |       76.24 |      76.40 |      32.27 |     32.52 |
| 20,000 spaced pseudos                       |    4,698.55 |      34.12 |   4,691.11 |     33.48 |
| 20,000 pseudos on separate lines            |    4,815.52 |     197.40 |   4,813.78 |    196.88 |

Ordinary corpus parsing was effectively unchanged. The targeted improvement removes repeated scanning; it is not a general parser speedup. The tradeoff is 1,997 → 2,066 states, 454 → 465 large states and 3,983,147 → 4,092,269 bytes of generated C. The node schema remains unchanged. Electric-pairing probes retained the baseline 536/570 and 512/570 keystrokes, so this change does not resolve Q016.

Incremental reparsing has two measured worst cases (runtime 0.27.0, Apple M1 Pro, native C harness, best of several runs):

- **Many top-level statements.** Every edit re-shifts each top-level item. A file of 16,573 one-line rules (729 KB) spends about 4.6 ms reparsing and 3.8 ms computing changed ranges per edit; a 729 KB stress file with 8,011 top-level items spends 1.9 and 1.4 ms. The cause is in the runtime, not the grammar: the parse table keeps the repetition shift beside each binary repeat reduction, so the runtime marks that reduction fragile, and `ts_subtree_compress` rotates repeat nodes without updating their recorded parse state, so chunks to the right of an edit fail the reuse state check. A runtime prototype that ignored the repetition shift when computing fragility kept 12,000 random-edit incremental trees and changed-range counts byte-identical but helped only edits near the end of a repetition; a complete fix needs both runtime changes upstream.
- **Very large declaration blocks.** The `property_name`/`tag_selector` GLR reduction is fragile, so an edit inside a block re-lexes and re-parses every declaration of that block and of each block enclosing it, and every nested rule in those blocks whose selector starts like a declaration, such as `a:hover`. One rule with 2,000 ordinary declarations reparses in 4.7 ms against 5.1 ms for a full parse, and one with 8,000 in 18.9 against 20.3 ms; 2,000 custom properties, which have no ambiguity, take 0.57 ms. Real files are far from this: over 335 local stylesheets, 10,050 random single-character edits reparsed in 0.017 ms at p50, 0.16 ms at p99 and 2.0 ms at most.

## Decisions and remaining debt

The architecture review considered retaining shared tables with simpler resource/execution ownership, pre-classifying statements in the scanner, and generating separate dialect tables. The first option preserves the smallest supported model. The statement-classification prototype changes incomplete-tree recovery and has failing acceptance evidence; separate dialect tables add generation/schema obligations without demonstrated net benefit. Neither is part of this migration.

The combined performance/memory review also rejected inlining the tested hidden selector/raw productions, imposing a hard character cap on recovery lookahead, and replacing ordered query captures with sorted matches: each changed existing trees or editing-time capture order. Hidden productions and long trivia carry recovery obligations even when they are absent from the public tree. Inlining `_complex_selector`, `_compound_selector`, `_simple_selector`, `_selector_list`, `_argument`, `_at_rule`, `_space_value` and `_value_atom` together (6 added conflicts, 473 large states) cut internal heap subtrees by about 16% and full parses by 10–13% with error-free trees unchanged, but changed ordered highlight captures in 1,003 of 12,000 random-edit states, so it is rejected for the same reason. The full highlight query also has a pathological ordered-cursor cost with thousands of intervening comments; changing query execution belongs to the host/runtime and needs its own ordering proof. Compiling the query takes about 51 ms per language entry with runtime 0.27, about 40 ms of it for the two `query_group` patterns. No exactly equivalent cheaper pattern was found, and dropping their comment tolerance would cut compilation to about 30 ms but lose `@property` on feature names with comments inside media ranges; they stay, because a host compiles the query once per session.

Follow-up recovery experiments confirmed that adding a never-emitted missing-block token alone does not fix Q016. In the inspected Tree-sitter 0.25.1 runtime, temporary recovery branches can reach their version limit before retaining the required reduction. Inlining selector-list/complex-selector dispatchers improves some incomplete heads but loses existing selector and function captures elsewhere. A zero-width boundary before a prospective property name also competes with keyword scanning for the lexer's single token-end mark. These experiments do not justify removing cross-line block lookahead or changing runtime limits.

A raw-identifier leaf prototype reduced hidden storage in a synthetic 1 MB value, but broader editing tests exposed a following block closer being captured as interpolation punctuation. It was rejected. Common-case allocation savings and unchanged valid trees are insufficient when damaged input loses existing highlighting. Recovery acceptance tests retain useful roles in unfinished selectors, function heads and nth formulas without freezing their entire erroneous CST.

Retain the fresh-process preview boundary, standard CLI HTML renderer, CSS adapter, atomic descriptor publication, context-specific grammar productions and required generated headers. Replacing them would need new contract/performance evidence. Repository file moves and a metadata generator do not remove a demonstrated obligation here.

The subsequent Q017 change removes the unbounded per-pseudo block search with one additional external token and no persistent scanner state. It also corrects a previously hidden descendant inside blockless selectors: `@extend :is(.b :hover)` now contains a `complex_selector` for `.b :hover`. Public node types remain unchanged. This is an intentional tree correction, not evidence that every previously accepted tree is byte-for-byte identical.

The declaration colon stays an internal token. Lexing it externally removes the forks at declarations that the large-block worst case comes from, but it raised incremental cost by 54–68% on the benchmark's small blocks, so it stays rejected on the editor hot path and that worst case stays documented debt. One shared content rule for different kinds of groups is rejected: merging selector arguments with call arguments alone needed new grammar conflicts, grew the large states by about a seventh, changed the node schema, and read whitespace in calls as descendant combinators, because the scanner and the lexer take their context from which tokens a group allows.

A stray block recovers as a missing selector or as a bare `@media` at equal cost, and the runtime then keeps whichever version it reached first, which differs between incremental and fresh parses. Dynamic precedence on the bare `@media` form makes the missing selector win in both; that form has no competing valid parse. An unfinished `*` hack such as `*zoom rhythm(90);` ties the same way between a declaration and a universal selector that swallows the next rule's selector; a `*` touching a plain name can only be the hack, so dynamic precedence on a touching `*` keeps the declaration reading. A touching `#{` lexes as the adjacent interpolation of a selector, which the property name does not accept, so `*#{$p}` never reaches this choice. A `*` that a line separates from its name gets no precedence, which would otherwise merge a stray `*;` line with the declaration below it.

Known baseline debt remains. A header whose group stays open past its first line can still absorb the following statements, and so can a top-level-style at-rule such as `@mixin` typed inside a rule above a declaration; a top-level `@media` header cut off by a declaration line leaves that declaration to the next rule's selector; a missing semicolon after a value that ends with interpolation, an unclosed `url(`, and an interpolated name typed on its own line above a declaration each put the next declaration's name in an `ERROR`; and punctuation after another statement on the same line above a declaration is not reported (Q016), except a compound start after a space, as in `color: red; .` or `color: red; #{}`, which is one `ERROR`. An unclosed `#{` with more text after it on its line pairs with a later `}`. An unpaired or empty attribute bracket, as in `&[d`, `&[d=` or `.b []`, absorbs the following statements, because no external token is valid inside `[` to end its line; only an operator before its value, `[a=]`, is accepted as an editing tolerance. An interpolation that continues a name, as in `&#{$p}(.x)` or `.a#{$p}(.b)`, still cannot take selector arguments: the name claims it before the `(` that would make it a pseudo call.

For future changes: establish the required behavior, identify its owner, challenge any new state or cross-layer classification, add contract evidence, implement, and measure affected hot paths. Remove replaced mechanisms rather than keeping an indefinite parallel path. Stop when remaining alternatives have no demonstrated benefit.
