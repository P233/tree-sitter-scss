# Architecture

This package supplies concrete syntax trees and ordered highlight captures for CSS and SCSS. It is not a Sass evaluator, CSS validator, editor, or document store. The [consumer contract](README.md#consumer-contract) defines the public behavior; this document describes its implementation boundaries.

## Ownership and dependency direction

```text
grammar.js ── generator ── src/parser.c + schema + runtime headers
src/scanner.c ──────────────┤
                            ├── Node binding ── native acceptance tests
queries/highlights.scm ─────┤
                            └── Rust/native binding ── native acceptance tests

scripts/grammar.js ── CLI / native build
        ↑
scripts/preview.js ── fresh inspect.js process + standard CLI highlighting
        ↓
preview-client.js ── temporary browser draft
```

| Boundary                                            | Owns                                                                            | Does not own                                                        |
| --------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `grammar.js`                                        | Syntax structure, fields, precedence, block contexts and external-token order   | Editor completion, semantic evaluation or runtime caches            |
| `src/scanner.c`                                     | Lexical boundaries, statement breaks, dialect identity and CSS lexer adaptation | Document state, source mutation, history or persisted scanner state |
| Generated `src/` files                              | Reproducible projections of the grammar and generator version                   | Independent handwritten decisions                                   |
| `queries/`                                          | Portable capture names and their ordered overrides                              | Host colors, fonts or editing commands                              |
| `bindings/node/`, `bindings/rust/`                  | Native language exports and access to schema/query                              | Build orchestration and preview lifecycle                           |
| `scripts/grammar.js`                                | Checkout root, CLI executable/options/cache, generation and native build        | Syntax decisions or preview state                                   |
| `scripts/benchmark.js`                              | Sample timing, per-dialect parser/tree lifetime and process resource reporting  | Parser allocation policy, editor latency or document history        |
| `scripts/fuzz.js`, `scripts/valid-inputs.js`        | Deterministic inputs, edit recording and baseline/candidate comparison          | Syntax recovery or Sass evaluation                                  |
| `scripts/recovery-acceptance.js`                    | Typed-state fixtures, exact counters and reviewed expectations                  | Sass verdicts or external editor fixtures                           |
| `scripts/recovery-cost.js`, `scripts/parser-cost.c` | Temporary scanner ablation, native timing and retained allocation measurement   | Runtime recovery switches or host fontification                     |
| `scripts/preview.js`                                | HTTP requests, file watching, build invalidation and published preview revision | Durable documents or browser drafts                                 |
| `scripts/preview-client.js`                         | Draft text, one active generation request, focus restoration and update notice  | Parser lifecycle or source-file writes                              |

`pnpm compare:build` builds the standalone comparison page and both grammars into `comparison/dist/`. Its browser worker owns parsers and queries for the page lifetime and deletes each completed parse tree. Diagnostics and difference markers are projections of that parse result; the page adds no parser or editor state to the library.

The Tree-sitter runtime owns trees and incremental reuse. A host edits the old tree before reparsing; undo is another host edit. No parser-local history or second source model exists. Native packages include generated C and headers so installing them does not require the generator. Their file lists are checked rather than inferred from repository layout.

## Complete input and statements being typed

The parser targets complete supported CSS/SCSS files. Root statements select rules or directives from their syntax; selector names are identifiers, with no HTML tag registry. Declaration blocks resolve properties at a declaration colon while retaining nested selectors, variables, at-rules and nested properties. Colons inside selectors and groups are not declaration boundaries.

The grammar owns interpolation, balanced groups and CSS `var()` arguments. The scanner recognizes the CSS `var()` name without reading its arguments, and never searches ahead to decide whether an interpolation opener is literal. Its lookahead resolves lexical boundaries (number/unit/subtraction, keywords, priority, namespace prefixes and complete `@if`/`@else` chains) and the statement breaks below. The `IF_END` token exists because adding or repairing an else must invalidate reuse of the previous complete if node.

Complete inputs, including those reached by repairing a damaged tree, must retain correct source ranges, structure and ordered highlight captures. Incomplete input is an editing state, not a second language: its tree shape is not a compatibility surface, but its scope is measured. A statement being typed or mistyped should stay one local `ERROR` and leave the following rules intact, because a host otherwise reparses, refontifies and refuses structural edits across the rest of the buffer on every key.

The typing contract inserts each prefix of a header, selector, declaration or variable into a document above a declaration, at a block's end, inside a nested block and between top-level rules. Statements outside the allowed region must keep their node types, subtrees and shifted ranges, with no `ERROR` ancestor. The line region permits only the inserted line to change; the block region also permits statements inside its enclosing block. Following top-level rules are counted separately as the tail. Both editor pairing and literal typing are measured; the contract includes keys that step over an inserted closer, while the incremental suites count text edits only.

An error-free reading can still change the next statement: an unfinished selector may continue as a descendant selector, and a partial known at-keyword such as `@med` is a valid unknown at-rule whose prelude can include the next line. Those readings must remain accepted. Conversely, the known limitations below still allow erroneous typed states to spread; the contract is a measured boundary, not a guarantee that every prefix stays on its line. Dart Sass classification in external comparisons distinguishes valid readings, hidden errors, spread and false errors; the repository acceptance runner uses only the parser's error flags and needs no Sass installation.

`pnpm test:recovery`, also run by `pnpm check`, compares every statement's counters and per-key flags with [one exact expectation file](scripts/recovery-acceptance.json). It covers the line/block contract, incremental typing and nearby highlight roles, incremental and fresh block-end parses, headers typed after complete statements and after unfinished selector, declaration or directive lines, and declaration-name typos. It records changed bytes and retained tail counts per edit, so exchanged regressions cannot cancel in a total. Emmet typing remains an optional external check because its fixtures belong to emmet2-mode. Add a reproducing fixture before adding a recovery site; record proposed expectations with `node scripts/recovery-acceptance.js --record /tmp/recovery-candidate.json`, compare them with the checked-in file, and explain each accepted difference. Never regenerate expectations merely to admit a regression.

### Sass reading boundaries

The parser retains source syntax without evaluating Sass. These readings matter to consumers even when parsing succeeds:

- CSS consumes CRLF as one hexadecimal escape terminator; SCSS consumes CR and leaves LF as selector whitespace. Thus `.x\31`, followed by CRLF and `b`, is one class selector in CSS and a descendant selector in SCSS. Both entries retain the original source positions. `bindings/node/css_test.js` checks this boundary and included-range parsing; scss2-mode also relies on it.
- Escaped spellings such as `s\65 lector`, `@m\65 dia` and `:l\61 ng` use generic function, at-rule or pseudo syntax. Escapes inside `An+B`, and escaped priority keywords, can produce errors.
- A media feature name continued by interpolation, such as `(max-#{$side} > 1px)`, is a value rather than a `property_name`. `.a /* c */.b` stays one compound selector, although Dart Sass emits a descendant selector. A name immediately after an attribute selector, as in `[x]a`, errors here although Dart Sass separates the selectors.
- Rules that Dart Sass also accepts without a block or a prelude are errors here: `@page`, `@scope`, `@keyframes` and CSS `@function` without a block of their own, as in `@page :first;`, and `@supports` spelled other than in lowercase without a prelude. A `;` ends a blockless `@page` or `@scope` header as one error.
- `fn()-1` contains a signed number after the call. Inside `url()`, `map.get` is one function name rather than a module access. A raw custom-property URL splits its scheme from the remaining address. These trees expose tokens, not evaluated Sass expressions.

The [known limits](README.md#known-limits) also cover unsupported complete syntax and typing states. In particular, a value's unclosed `/*` can be read as two operators when no closing `*/` exists later in the file. That case can have no `ERROR`; `comments_test.js` records the debt and verifies incremental repair when the close is inserted.

### Recovery principle

Tree-sitter recovers by a global cost search that the scanner steers only through token boundaries, so the parser cannot guarantee that an error stays on its line. Three runtime behaviors set the limits:

- Pruning keeps the version that has paid less so far. A version that ends a statement at a line break can pay for two errors there, while one that reads the next line into the statement pays for its second error later, after the first version is pruned. Incomplete map entries and a dangling `.` or `!` in a value take the next declaration this way.
- Recovery resumes in the shallowest earlier state with any action for the lookahead, even a reduce that then fails. The selector state that `@extend` shares reduces on `}`, so recovery there skipped a block's `}` and left the block open to the end of the file.
- Versions whose error costs differ never merge. A second path that differs by one skipped character keeps two versions, and no subtree reuse, until the cost difference, multiplied by one more than the nodes parsed since the error, exceeds 1,800.

Every recovery change follows these rules:

- **One mechanism.** An unfinished statement ends where no valid reading continues it and the text after it starts another statement: at the line break before a declaration, a rule line, an at-rule or a block's `}`, or on its own line before a `}` or a declaration. The [site table](#statement-breaks) gives each site's exact test. The scanner applies this test at three points only:
  - before a token shifts in an ordinary state, as in the punctuation breaks and the header, variable and typo claims;
  - at a line end inside a statement, as in selectors, values and groups;
  - in recovery mode at a newline.

  No other kind of site is added. A claim that rereads every complete statement of a common kind costs every complete file; one for `@include` lines added 4.8% lexer advances on a large real SCSS file.

- **Cost.**
  - Complete inputs keep their trees, and the scanner work a site adds to them stays within the [scanner ablation](#recovery-cost) targets. Count lexer advances in an instrumented copy, since parse timing cannot resolve such differences.
  - Recovery-mode code advances only after it sees a line break, because a parse version that finds no valid token lexes again in recovery mode, on complete input too.
  - Recovery settles on one parse version within a few lines.
  - Per-key typing p95 does not regress against a layout-only control build.
- **No hidden errors.** A break that a statement list accepts is emitted only in recovery mode or in a state that rejects it, where the break is itself the error. A punctuation break lexed again in the statement list is the exception: with no error before it, as after `.a {}.` above a rule line, it hides one, and each such case is a known limit with a test.
- **Stop rule.** A case that needs a different runtime pruning or recovery search stays a known limit instead of gaining a site. So does one that needs a restructured grammar, unless the change passes the gates for parse states, large states, query compile time, tree memory and incremental reparse time, and leaves no typed state worse.
- **Acceptance.** No typed state in `pnpm test:recovery` gets worse. A key between a repaired state and one still broken may change more of the file, and the commit lists such keys. Complete-input, valid-edit and seeded random-edit comparisons against the previous scanner change no error-free tree and hide no error, and the sanitizer fuzz and scss2-mode's checks pass.

### Statement breaks

A statement break is an external token that selector and value states reject, so recovery returns to the enclosing statement list; statement lists and raw statement items accept it. A cut-off header or a line of leading punctuation instead gets a token no state accepts, so the parser skips that text as one error. Each site decides from the text after it:

| Site                                                                                                                           | Next text                                                                                                                                                                                                                                                                                                | Token                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Whitespace in a selector, on its line or across a line break                                                                   | A declaration name, or across a line break an at-rule                                                                                                                                                                                                                                                    | Statement break                                                                                                                                                                       |
| Punctuation that cannot complete a selector line, or an interpolation ending one, and its relex after errors                   | A declaration name on the next line, a rule line after a `.`, `:`, `%` or `#` needing a touching name, or after a selector an at-rule there                                                                                                                                                              | Statement break including the punctuation and interpolation, before a declaration or rule line also the line break and indentation                                                    |
| `@` with a block at-rule header in a statement list, or `@else` after an `@if`                                                 | Before the header's block: a declaration line, a `}` (but for a block's `}` after a rule Sass accepts without a block), or a rule line led by a `.` or `:` name, or outside Sass control expressions by `%` or a non-hex `#` name (never after `@at-root` or `@page`), or for `@page` and `@scope` a `;` | Never-valid header token covering the header (and the trivia before `@else`); one that a block's `}` cuts off in a statement list is valid instead, followed by a never-emitted block |
| A later line of a declaration value, an unclosed `url(` or any other statement interior but a raw value or raw at-rule prelude | A declaration line, after which no group still open around it closes; in an expression, also a rule line led by a class or pseudo name                                                                                                                                                                   | Statement break at the end of the line above                                                                                                                                          |
| A block statement-list variable name, optionally followed by its colon                                                         | Only whitespace to the next line, which starts a declaration                                                                                                                                                                                                                                             | Never-valid token covering the variable name and colon                                                                                                                                |
| Recovery mode at a newline                                                                                                     | A whole declaration line, with no enclosing group closing later, or a line led by a `}`                                                                                                                                                                                                                  | Nonempty statement break covering the newline and indentation                                                                                                                         |
| A line-leading `>`, `+`, `~` or `#` in a statement list                                                                        | A declaration name on the next line                                                                                                                                                                                                                                                                      | Never-valid header token covering the punctuation and interpolation                                                                                                                   |
| A statement-list name with a colon touching it and a second name, as in `op:acity: 0.4;`                                       | The second name's own colon, then no block on the line and `;` or `}` on it, or its end before `}` or a declaration line                                                                                                                                                                                 | Never-valid token covering the line through its `;`, or up to the `}` or the line's end                                                                                               |

A never-emitted `_raw_prelude` token is valid only in raw at-rule preludes, so the scanner tells them apart from other statement interiors. A declaration name may carry dashes or same-line interpolation. A colon touching a name, as in `display:flex`, may instead start a pseudo-class, so such a name counts only when its line ends as a declaration does. A declaration line ends its value with `;` on that line, outside any group still open around it. Inside an open group, a `url(` payload or a header's group, the group must also never close later, and an exhausted budget counts as closing; a header checks each later line, where a name must meet its colon on its own line, and stops at a line that starts a declaration without ending as one, such as a map entry. Lookahead sites skip strings, block comments and same-line interpolation; escape and group handling remain site-specific. The claimed headers are `@if`, `@each`, `@for`, `@while` and `@at-root` as spelled, and `@page`, `@media`, `@supports`, `@container`, `@layer`, `@scope` and `@starting-style` in any case. Each also ends at a `}` outside any group that closes after it, since recovery that skipped the `}` could continue the header with the next rule and leave the enclosing block open to the end of the file. A rule Sass passes through without a block may instead end its statement at its block's `}`: `@container`, `@layer` and `@starting-style`, and `@media` or `@supports` spelled other than in lowercase; a top-level `}` closes nothing, so it still ends the header. `@page` and `@scope`, which Sass also passes through without a block, still end there inside a block, since the grammar requires their blocks. Inside a block, a header that the `}` cuts off takes a token the statement list accepts, followed by a block the scanner never emits, so the error is found at the `}` rather than at the `@`. Recovery from a selector line left unfinished above, which an at-rule on the next line ends, then resumes in the statement list without a second error at the header, and the line and the header form one `ERROR` instead of the selector skipping the `}` and continuing with the next rule. A rule line may continue the selector prelude of `@at-root` or `@page`, and a Sass expression may continue with an unquoted `#name` or the `%` operator, so such rule lines end neither. `@mixin` as spelled and `@function` in any case are claimed only when their `@` does not start its line: a definition at the start of a line is taken as top-level, where claiming would strand its body, while a nested header left unclaimed takes the next rule's block and leaves its own rule open to the end of the file. The whitespace skipped before the `@` decides this, or the start of the text when there is none; asking the runtime for the column rereads the line, which makes long single-line files quadratic. `@extend`, which has no block, takes the same claim before a declaration line; it may end at `;` or at its block's `}`, and its selector list may continue on the next line. A break decided across a line is empty and sits at the end of the line above, so the next line keeps its whitespace; a same-line break includes the whitespace or punctuation it covers. Only a marker needing a touching name ends its line before a rule line; after a comma, a combinator or a whole compound the next line may continue the selector. A punctuation break before a declaration or rule line, with no comment between them, also covers the line break and indentation: recovery that skips the break then resumes at that statement, not at the line break, where a second path into the same statement list would differ from the first only by the skipped punctuation and keep two versions, as the [recovery principle](#recovery-principle) describes; each key then reparsed about 1,800 nodes. Recovery mode emits only this newline break and never advances at other characters; its all-token-valid context cannot choose a string, comment or value host. Every helper spends one local budget of 1,024 steps; interpolation in a lookahead must close on its line.

Two grammar tolerances complete the set. A bare `$` lexes as an incomplete variable prefix. Recovery keeps it as a one-character error or, as in `#{$}` and `fn($, 1)`, inserts the never-emitted missing name; either way the error stays in its statement and the enclosing callable keeps its scope. An attribute operator before its value, as in `[a=]`, parses without an error, although Sass rejects it.

A new site must also lower a typing counter or move a case out of the `recovery debt stays visible` test; a recovery test checks one-version convergence through the parse log for lines above a declaration. A break must never be emitted where identifier recovery lands: a compound-start break lost declaration captures in 51 of 40,000 seeded edits, against 5 for the adopted sites.

Recovery cost must be remeasured when a site changes; [the scanner ablation](#recovery-cost) keeps its baseline and workload definitions reproducible. Historical typing measurements motivated the sites, but do not establish the cost of a later scanner.

## Grammar and query shape

Hidden helpers that only dispatch are listed in `inline`: they keep grammar names without allocating runtime nodes, which cut retained tree storage by 18–33% at the cost of more declared conflicts and states. A semicolon-ended `property_declaration` expands its body instead of wrapping `_property`, about 88 bytes of retained tree per declaration; `_property` remains only where it is aliased or wrapped: a block's final declaration without `;`, `feature_query` and CSS `@function` bodies. Declaration names and value words rename `_interpolated_identifier` to `property_name` or `plain_value` instead of wrapping it, so a name costs one node instead of two. Every context still shares that one reduction, which defers the property-or-selector and module-or-selector decisions to the token after the name. `tag_selector` keeps its wrapper: its reduction is where the declaration colon forks, so each reading lexes the token after the colon in its own state. A declaration whose value is one atom, 91% of that corpus's, holds the atom directly instead of `_value`, `_space_value` and `_expression_atom`. Precedence 1 picks that reading statically, and it must span from the atom to the end of the declaration: Tree-sitter resets the precedence of a `prec` rule's last step when more steps follow, so precedence on the atom alone never reaches the reduction. A one-child hidden node costs 88 bytes and an inline leaf nothing, so retained memory follows token density rather than file size.

Keep the CSS adapter, atomic descriptor publication, context-specific groups, generated headers, fresh-process preview and standard CLI HTML renderer. They protect concrete lexical, concurrency or tooling boundaries. Generic flattening of all groups loses distinctions between selectors, call arguments, query conditions and raw CSS.

Complete control-chain grouping and public editor-facing structural wrappers have downstream consumers; removing them requires a coordinated schema/query and host-consumer migration. Math functions such as `calc()` and `min()` parse as ordinary calls, so a constant such as `pi` in them is a plain value: their own argument grammar took 244 of 2,192 parse states and 61 of 494 large states, and about 11% of the library. Coarsening map keys or query-feature colors is a separate behavior decision.

A query group names a boolean or range feature `property_name`, as `feature_query` does, so the highlight query needs no structural pattern for it. Both readings of a group parse until it closes, which keeps unary signs and compound left values such as `1 / 2 < aspect-ratio`; dynamic precedence prefers the feature test, and a leading name over one after the value side, as in `(width < height)`. A feature name starts with a word or `--`, so `(#{$query})` stays a value. A new query pattern needs capture and compile-time evidence. Query, condition and type operators wrap an anonymous `|` child that one `(operator "|")` pattern matches: a pattern under a `query_statement`, `query_group` or `type_annotation` parent makes query analysis enumerate the hidden value rules below it, and those parent patterns took about a third of the query's compile time. Trivia `block_comment` is one token: as a nonterminal extra it kept about twice the hidden repeat nodes, 18% of retained tree storage and 11% of parse time over the real-file corpus. The token makes the former `query_statement` and `query_group` operator patterns about three times costlier to analyze, so a parent pattern over query or value nodes needs compile-time evidence against the current grammar.

A class selector aliases its existing anonymous `.` child to `class_dot`, so the complete selector capture colors the prefix without a delimiter capture and a later override. This adds no wrapper node. Verify alias changes against complete tree structure and ordered captures, with only the intended token and capture changes accounted for; host face equality alone cannot establish schema compatibility.

## Rejected designs

These were measured and rejected; revisit them only with new evidence.

- Lexical disambiguation of the declaration colon, where 99% of GLR forks occur: full parsing 11% faster, but incremental edits 54–68% slower, because node reuse must look up the last external token of every reused subtree.
- Plain inlining of `_interpolated_identifier` or the value-side `_expression_atom` does not converge (20 to 40 or more new conflicts); inlining `_value` raises large states from 463 to 725, over the budget. Selector-side inlining lost recovery highlighting.
- A leaf `property_name`, the name token aliased at declaration sites: the colon decision becomes a shift that `_interpolated_identifier`'s right associativity wins without forking, so `th:first-child { … }` after a declaration became an error, with 15 more conflicts and 30 more large states.
- One shared content rule for all groups: states rose from 2,071 to 2,208, the node schema changed, and 217 of 732 snapshot trees changed.
- Narrowing the CSS `var()` fallback to typed atoms: valid `var(--x,[a;b])` fails and a damaged raw interpolation takes the block's `}`. An ordinary block for CSS `@function`: Dart Sass passes `result:` values through verbatim. Dropping `raw_statement` for unknown at-rules: 2% smaller, but future at-rules would carry `ERROR`.
- Escaped keywords in the generated lexer: parser.c grew from 3.98 MB (its size then) to 9.29 MB and parsing was 3–7% slower, for no escape in the 499 files of an earlier local corpus.
- Highlight patterns over `query_group` children to give feature names the property role: each costs about 10 ms to compile in Emacs 31.1, and the two it required took 19 of the query's 29 ms per language entry.
- Other statement-break sites: a cross-line search for a spaced colon's block, a line-leading `*` site and text-host interpolation pairing changed none of the typing counters with editor pairing. Pairing helps only where an editor leaves `#{` unclosed, and would reinstate the window that limited complete interpolation.
- One break for every expression position, which would also end unclosed calls, damages recovery inside maps and arguments.
- Accepting blockless `@page`, `@scope`, `@keyframes` and CSS `@function` in the grammar: every formulation tried moved Tree-sitter's parse-state and lex-state merging, which decides the token recovery sees after an error. The best, separate aliased rules (+28 states, +12 large), still made 5 unpaired typed states and 4 of 20,000 seeded edits lose the rest of the file; shared hidden heads, which needed 9 fewer states, lost the rule after an unfinished top-level `@debug` in 64 typed states.
- Dropping the bare-`$` prefix so that `variable_name` becomes a leaf: 1.5% less retained tree on a variable-heavy file, but with editor pairing 23 keys of the typing contract and 19 incremental typing keys spread further, against 3 and 2 that improve, and `#{$sel}` typed at a nested block's end takes the next rule.
- A missing-block token and a zero-width break before a name damaged recovery or conflicted with keyword tokens; per-comment lookahead was quadratic.

## Invariants

- CSS and SCSS share one generated parsing table, node schema and query. Language selection is immutable per entry.
- The scanner serializes zero bytes and allocates no heap storage. Each lookahead is local to one invocation and bounded by its 1,024-step budget; there is no interpolation stack.
- Whitespace before a colon uses one external token shared by declarations and selector combinations. The grammar resolves the readings. Selector whitespace reads at most the next declaration line (its name and colon, and the rest of that line when the colon touches the name); it never searches later lines for a block, a search that made 20,000 multiline pseudos parse about seven times slower.
- A block after a colon with no whitespace after it starts a selector whenever one parses, as in Dart Sass; `_nested_property`'s negative dynamic precedence states this. Without it, the two equal-cost readings merge after the block and Tree-sitter keeps whichever version it created first, so an unrelated grammar edit can turn `th:first-child { … }` after a declaration into a nested property.
- CSS text hosts keep interpolation literal. SCSS statement comments and strings use the ordinary expression grammar, so a quote or `*/` inside a nested expression cannot terminate its outer host prematurely.
- The CSS descriptor is published once with acquire/release synchronization for concurrent native callers.
- CSS CRLF normalization preserves original source positions. The generated keyword lexer has no identifier escapes to normalize; external scans use their dialect-aware escape routine.
- Grammar external-token order and the scanner enum must agree. Generate and test after changing either side; never hand-edit generated C to change syntax.
- `pnpm generate` removes Tree-sitter's optimize-off pragma from the large generated lexer. `--check` performs the same step; unknown pragmas fail rather than silently changing compilation policy.
- Complete-input compatibility includes nodes, fields, anonymous punctuation, ranges and ordered captures. Successful parsing alone is insufficient evidence.
- All development CLI invocations use `runTreeSitter` and the current checkout's `build/tree-sitter` library cache. Same-named grammars in another checkout cannot supply its library.
- Foreground CLI commands inherit the terminal. Internal generation/preview calls capture output with a 30-second timeout and 16 MiB limit.
- Build-source changes invalidate the preview binding. A fresh inspector process loads the rebuilt module; browser drafts do not rebuild it or overwrite source fixtures.

## Independent validation

`pnpm check` runs lint, formatting, generated-file equality, native build, corpus/highlight assertions, Node and development tests, deterministic valid-input checks, Rust tests/formatting, package contents and preview export. `pnpm check:generated` fails when the generated parser exceeds 525 large parse states; source size and state counts do not substitute for performance measurements.

Native tests cover complete syntax and highlight roles, source ranges, dialect boundaries, incremental context changes, and repair back to complete input. Resource smoke tests parse deeply nested or damaged input in a subprocess with a timeout, without requiring a particular erroneous tree. `recovery_test.js` checks each statement-break site, same-line typos and unfinished variables by the error text and the intact later rules, not by the whole erroneous tree, and keeps the known gaps visible.

`pnpm test:fuzz` replays 5,000 seeded single edits per language entry over `test/corpus`, `test/highlight` and `examples`. Each case compares fresh and incremental trees and ordered captures, then reverses the edit and compares with the original. Differences fail only when the expected fresh/original input is error-free; error-input differences are reported. Development tests include a shorter run.

For baseline/candidate comparison, rebuild each checkout and use the same runner, seed, case count and optional corpus file list. Inputs come from the invoking checkout:

```sh
node scripts/fuzz.js record --repo /path/to/baseline --corpus /path/to/file-list.txt --out base.jsonl
node scripts/fuzz.js record --corpus /path/to/file-list.txt --out candidate.jsonl
node scripts/fuzz.js compare base.jsonl candidate.jsonl
```

Comparison rejects misaligned or malformed recordings. It fails on baseline error-free tree changes, ordered capture changes even when trees agree, or candidate incremental/repair failures on error-free input. Error-input tree and capture differences are informational. A baseline may accept malformed syntax under an older tolerance; inspect such differences against the complete-input contract instead of treating the baseline's `hasError` flag as a language validator. Removing a tolerance does not authorize unexplained changes to valid syntax.

`pnpm test:valid` uses the same recorder with every template in `scripts/valid-inputs.js`: multiline headers, selectors and values; touching or spaced colons; LF/CRLF and indentation variants; escapes, raw preludes, and header comments long enough to exhaust the lookahead budget. Each original is parsed directly, then edited at the statement start and end and repaired. Expected original validity is declared independently of either parser. The quoted-URL comment cases remain explicit known errors and are reported separately; new failures are never filtered out. Add a complete continuation to this suite for each new recovery site.

```sh
node scripts/fuzz.js record --suite valid --repo /path/to/baseline --out base-valid.jsonl
node scripts/fuzz.js record --suite valid --out candidate-valid.jsonl
node scripts/fuzz.js compare base-valid.jsonl candidate-valid.jsonl

node scripts/fuzz.js record --suite valid --sass /path/to/node_modules/sass
```

The optional Sass check compiles every original, including the declared parser gaps, and reports the Sass implementation version. A rejection fails the run. Sass acceptance supplements the parser's syntax assertions; it does not define the tree or highlight schema.

## Performance measurements

Run `pnpm benchmark` to rebuild and measure the native binding. For already built checkouts:

```sh
node --expose-gc scripts/benchmark.js --repo /path/to/baseline
node --expose-gc scripts/benchmark.js --corpus /path/to/file-list.txt
```

The optional corpus is a newline-separated file list. Every input is exercised in both language entries; `errorFiles` identifies workloads that are not wholly accepted in a dialect. Compare ordinary reading performance only on supported, error-free workloads.

The runner compiles the highlight query once per language and reports its cost separately. Full-file rounds time parsing, ordered `Query.captures`, and their combined elapsed time. They have two warmups and nine measured rounds, batching small/nested workloads 1,000 times. A numeric replacement in a 1,000-rule file separately measures incremental parsing, with 20 warmups and 200 samples. Two typing workloads type 29 statements key by key, with editor-style pairing of `{`, `(`, `[` and `"`, into a fresh parse of another 1,000-rule file: on a blank line above `width: 1px;` and before that declaration on its own line. Every key is timed; `changedKB`, `keysChangingQuarterFile` and `errorKeys` are deterministic and compare exactly between revisions. The interpolated-values workload alternates 500 declarations missing their semicolon with 900-character interpolations, so value lookahead must charge interpolation to its budget.

Before samples, the runner requests GC when exposed and yields to let queued native finalizers run. Cleanup and validation are outside timing. Each dialect releases its final parser/tree before the final resource report. `maxRssKiB` and `processRssAfterCleanupBytes` include the runtime and harness; they are not live tree allocation sizes. Hashes identify sources, query and workloads, but do not certify a stale binary: rebuild both revisions before comparison.

Alternate baseline/candidate order on the same machine and compare repeated runs with matching runtime and workload hashes. Spaced/multiline pseudo chains and long comments retain coverage against repeated scanning of the remaining source. Report parsing separately from capture-query time; neither includes host font-lock, layout, repaint or GUI latency. Generated size alone is not evidence of a speedup.

### Recovery cost

```sh
node scripts/recovery-cost.js
node scripts/recovery-cost.js --repo /path/to/checkout --corpus /path/to/file-list.txt
```

The runner needs a POSIX C11 compiler (`CC` overrides `cc`) and builds two native executables in a temporary directory with the same generated parser and Tree-sitter runtime, linking the scanner last so both place the shared code at the same addresses. The second disables scanner recovery decisions only; grammar recovery states, `[a=]` tolerance and runtime error recovery remain. The runner refuses a scanner other than the one the ablation was reviewed against, by hash: a new recovery decision can match none of its source landmarks, so a scanner change needs the ablation reviewed and the hash updated. Source landmarks must still match. `--repo` therefore measures another checkout only when its scanner is the reviewed one; measure a different scanner revision with that revision's own runner. Supported complete inputs must have identical tree fingerprints before timing; erroneous workloads are reported as non-comparable. The deterministic valid-input suite and corpus comparison must also pass against the disabled scanner when changing the ablation.

Defaults are seven alternating process pairs with three warmups and 25 measured parses per process, compiled at `-O2`. The parse ratio compares the medians of the process medians; tree deletion is outside timing. A separate counted-allocator run reports requested bytes released when the tree is deleted, with the parser still alive, and checks cleanup after deleting the parser. This measures retained tree allocations, not RSS or peak memory. Output retains each process's median and minimum, compiler and runtime identity, and source and workload hashes. Run on an otherwise idle machine; compare the same workloads and rerun a threshold-crossing result before accepting it.

The acceptance target on a representative large real file is at most 3% extra parse time and 1% extra retained tree memory against this scanner-disabled baseline. Record the input hash; also report the bundled stress fixture and generated flat, nested and 20,000-rule selector workloads separately. The target is not evidence that a candidate passes. An over-budget result remains a failed acceptance item; do not raise the limit to admit it. Further recovery work must reduce an existing cost or demonstrate no measurable increase, and must still preserve complete-input behavior.

Three local Apple M1 Pro runs with Clang 21.0.0 and Tree-sitter 0.25.1, 11 rounds each, measured the local 692 KB `big.scss` (SHA-256 `ea288e64ca38…`) at 2.67–2.78% extra parse time in SCSS and 2.32–2.38% in CSS, with 0.12% extra retained tree memory, and the 248 KB `bigc.css` (`8b0e5492f25e…`) at 2.73–2.81% and 2.31–2.41%, with 0.04%. Both stay within the 3% parse target by only 0.19–0.7 points, so a small scanner change can cross it. The generated workloads measured 2.2–3.0%, and the stress fixture 3.4–3.7% with 0.67% more tree memory; CSS rejects parts of that fixture, so its CSS timing is excluded. The later unfinished variable and `@extend` claims add 0.34% scanner advances on `big.scss` and none on `bigc.css`, and 80 bytes of tree per `@extend`, which raises the stress fixture's extra tree memory to 0.71%. An 11-round run of each scanner differed by at most 0.1 points on the real files, while generated workloads that run none of the added code moved by up to 0.5 points. The recovery-mode newline break adds 0.13% and 0.07% scanner advances on those files, and the benchmark's 500 missing semicolons before 900-character lines parse about 10% slower, since recovery checks each of those lines once more. These results exclude grammar recovery states: the bare-`$` branch makes every `variable_name` a node wrapping its token, about 1.5% of `big.scss` tree memory, while the cut-off header's states add no tree memory and left real-file parse time unchanged.

## Known limits

The README's [Known limits](README.md#known-limits) lists the gaps that editing real stylesheets meets. These causes, including rarer gaps, constrain changes here:

- An incomplete map entry such as `$map: (key:)` or `$map: (key: value, o)` can take the following declaration as its value and insert a missing `)`. At the top level, where the next line is a rule rather than a declaration, the error can take the following rules. Closing the group and ending the variable require separate recovery steps.
- Dangling `.` or `!` in a value can absorb the next declaration. A break covering the punctuation still has to be read again in a statement list after the missing semicolon; accepting it there also hides standalone malformed `0.` and `!` lines. Skipping the punctuation as an invalid token requires another recovery and can still lose the next declaration.
- Punctuation after another statement or a `{` can join a statement break before a declaration on the next line without an error, as in `color: red; ,` followed by `width: 1px;`; so can a lone `.`, `:`, `%` or `#` touching a `}`, `;` or `{` before a rule line, as in `.a {}.` followed by `.b {}`. The same comma before the closing `}` does report an error. A never-valid token at the break would make recovery merge the rest of the file.
- In a short file, a last rule left open after a complete declaration can make the whole file one `ERROR`: Tree-sitter's recovery inserts the first missing token by symbol order whose state can reduce at the end of input, here a name rather than `}`.
- Large declaration blocks can limit incremental reuse because of selector/property ambiguity.
- Inside an argument list or query group, a declaration line also reads as further arguments, so recovery may skip the break and keep the group open; with a value that starts with a call, as in `width: calc(…)` below `margin: fn(c,`, that declaration loses its name while later rules stay intact. A cut-off control or at-rule header is claimed at its `@` instead, unless a line of its open group starts a declaration without ending as one, such as a map entry; that header takes the rest of the file.
- A header cut off before a rule line led by a tag name, `&`, `*`, `[`, a combinator or interpolation, or in a Sass expression by `#` or `%`, is left to recovery, whose costs decide whether it stays one error: `@scope (.a)` before `&:hover {`, `~ .y {` or `#{$s} {`, and `@for $i from 1` before `#main {` or `%y {`, take the rest of the file. Inlining `_compound_tail` or making `block_comment` a token, each alone, once made a cut-off `@for` take the next rule; parse-table changes need the recovery tests even when complete trees are unchanged.
- A `}` in a header line ends the block around the header unless it sits in a group that closes after it, so `@media (min-width: 1px} {` nested in a rule closes that rule, and its block and the next rule lose their trees. Reading such a `}` as stray whenever the header still reaches its own `{` kept those local but brought back whole-file collapses such as `@for $i from 1 }through $n {`.
- A header cut off by its block's `}` can still take the rest of the file when it is typed on the line of a selector that leaves a pseudo-class argument list open, as in `&:not( @media screen`. Recovery from the other unfinished selector lines reaches the line break before the `}`, where it ends the statement.
